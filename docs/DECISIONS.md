# 決策紀錄

開發時遇到需要判斷的地方，都選「最容易回頭」的做法先繼續，記在這裡：決定、理由、替代方案。編號依時間排。

## 共通

### D0-1 測試只用 Node 內建，不加套件
- 決定：單元與模擬測試用 `node --test`（`npm test`），端到端用環境裡預裝的 Playwright（`require('playwright')`）與 Node 內建 http 伺服器（`npm run test:e2e`）。`package.json` 只有 scripts，沒有 dependencies。
- 理由：app 本身沒有建置流程與相依；測試工具也不該讓部署多一個步驟。
- 替代：Vitest／Jest（要 npm install）。之後需要覆蓋率報表再考慮。

### D0-2 測資是程式產生的合成樂譜
- 決定：`test/helpers/songs.js` 用固定種子產生 12 首結構各異的 MIDI（快音群、弱起、不規則小節、未量化錄製、SMPTE、卡農與長休止、四聲部、鋼琴和弦與踏板、鼓、慢板長音、單聲部），測試一律掃整個測資庫，不針對某一首調參數。合奏測試另外在每首後面加一個「在每兩個起音正中間放一顆音」的伴奏聲部（只有兩個聲部的歌兩個都被指派時本來沒有伴奏，量不出伴奏的問題）。
- 理由：規則要對任何 MIDI 成立；真實曲目有版權疑慮，也不知道哪些結構被涵蓋。
- 替代：之後可以把使用者的曲庫匯出幾首放進 `test/fixtures/`（要確認授權）。

### D0-3 「單人、現有模式手感不變」用逐筆基準比對
- 決定：`test/fixtures/onset-single-baseline.json.gz` 是用**原本的 commit（e8c1553）**的排程器跑出來的：12 首 × 前兩個聲部 × 鍵盤／揮手 × 三種速度（含偶爾連按）共 138 段，記下每一次合成器呼叫的時刻、音高、時間戳。`test/baseline.test.mjs` 用目前的程式重跑並逐筆比對。**力度不比**（階段 2 刻意依按鍵位置與揮手改變力度）。
- 理由：「手感」最可靠的定義就是「每個音什麼時候響」；比對逐筆時刻比任何統計都嚴。
- 替代：只比統計（平均延遲等），抓不到個別音的改變。
- 重新產生的方法：`git worktree add /tmp/base e8c1553 && node test/tools/gen-baseline.mjs /tmp/base/src test/fixtures/onset-single-baseline.json.gz`。

## 階段 0：合奏檢查

模擬方法：`test/helpers/sim.js` 用假合成器記下每一次呼叫、12ms 一次 tick（同 `midiPlayer.js`），演奏者用「機器人」：照排程器自己公布的下一個要按的起音、照自己的速度從自己上一下接著數（被合奏拉走之後從新位置繼續），可加速度倍率、手抖、漏按、多按、停手再回來。檢查項目（`test/helpers/metrics.js`）：放行卻不是當下發聲、伴奏擠成一團、伴奏比帶頭的人晚、帶頭的人來回跳、同一顆音發聲兩次、卡音、代打交還多推一格。

找到並修掉的問題（這些測試在原本的程式上會失敗，修完通過）：

### D0-4 落後跳到聲部結尾時回報「放行」卻沒有聲音
- 現象：不是帶頭的人落後太多，按下時合奏已經走過他最後一個音，落後跳把剩下的音都跳過，`trigger()` 卻回傳 true、按鍵記錄是 `released`。
- 決定：這種情況記成新的結果 `late`、回傳 false（他的聲部已經結束）。**不補放走過的音**：會在錯的位置響。
- 替代：補放最後一個音當回饋。放棄理由：跟合奏對不上，而且「不加檔案裡沒有的音」之外，也不該在錯的時間放原檔的音。

### D0-5 兩個不穩的人在一兩秒內來回交棒
- 現象：帶頭的人停住 → 交給第二位 → 第二位一秒後也停住 → 換回第一位（漏按、手抖多的兩個人時常見）。伴奏在兩人之間跳。
- 決定：新增「最短帶頭時間」`ENSEMBLE.LEADER_TENURE`＝max(2 拍, 1.2 秒)：換上來的帶頭者在這段時間內不會因為停住（overdue）、多數決被換掉，名單更前面的人恢復後拿回帶頭（return）也要等現任帶滿。離開鏡頭（absent）不受限。
- 代價：新帶頭者真的停住時，伴奏最多多等約 1.2 秒。
- 替代：加大第一段寬限。放棄理由：會讓所有換人都變慢，連第一次換人也是。

### D0-6 剛「落後跳」過的人馬上被交棒
- 現象：晚進場的人第一下就落後跳到合奏位置，這時帶頭的人剛好出狀況，帶頭交給他；他的位置是合奏給的不是自己的節奏，0.4 秒後又出狀況換回來。
- 決定：落後跳過的人要連續 `ENSEMBLE.JUMP_RECOVER_PRESSES`（2）下同步（同步／稍快稍慢）才有資格接手帶頭；現任已經不能帶（沒有人、停住且不算正在彈、被代打、彈完）時例外，免得沒人帶。
- 替代：跳完直接讓他帶、但把合奏錨點拉回他之前的位置。放棄理由：合奏會倒退。

### D0-7 跳位置的目標 tick 浮點誤差
- 現象：換帶頭者跳位置時目標是 `9599.999999…` 而不是 `9600`，結尾剛好在 9600 的音被當成「還在響」追音，發出一個 0 長度的音。
- 決定：跳位置的目標（換帶頭、落後跳、進入代打）離整數 tick 不到 1e-6 就當成那個整數（`snapTick`）。

### D0-8 換帶頭跳位置不算「伴奏擠成一團」
- 換到一個比合奏超前的人時，合奏照規則跳到他的位置（垂直切片：中間還該響的追音、整顆在身後的跳過），他的音與伴奏同一刻響。跳點前後兩個音靠得近是這條規則的結果，量「擠成一團」時排除換帶頭那一刻起 60ms 內的音。
- 替代：合奏用加速追上去（不跳）。放棄理由：新帶頭者按下去的音跟伴奏會有一段對不上，違反「觸發那一下當下跟合奏一起響」。

檢查過、沒有問題的：代打交還（77 種「回來的時刻 × 歌」，回來的第一下一律放出電腦還沒放的第一個起音或接手剛放的那一下，沒有一次多推一格）、離開鏡頭一秒代打、暫停續播、播放中互換聲部、主執行緒每 0.7 秒卡 80ms。

### D0-9（階段 1 時發現）代打重建佇列時重複排了已送出的音
- 現象：合奏重新對時（換帶頭、拍子模式開始一拍）會重建被代打的人的佇列（`_substituteFrom`），lookahead 已經帶時間戳送出、自動放行還沒到的那顆音被再排一次，響兩次。原本的程式在換帶頭時也走這條路。
- 決定：重建時跳過已經發聲過的音。混合模式的掃描測試（`test/modes.test.mjs`）抓到的。

## 階段 1：演奏模式

### D1-1 三層的定義
- **起音（onset）**：原本的行為，一行都沒改（逐筆基準測試保證）。
- **音樂家（musician）**：分組跟起音一樣（只併真的按不及的近距起音），差別是「他按的每一下都算」：去抖只擋 50ms 內的機械彈跳、估速視窗 3 個間隔（速度跟著 rubato 走）、揮手超前不鎖（可以帶到前面）、鍵盤的音長由放開決定、力度完全由按法決定（階段 2）。
- **拍子（beat）**：一下帶一拍。拍子單位（`src/midi/beats.js`）＝同一拍裡他的所有起音，拍內的音照樂譜依他的速度由電腦補上（沿用起音模式「組內自動放行」的機制）；不揮，這一拍就不會開始。音長照樂譜（不看放開）。
- 「音值」我解讀成力度（長短已經另外列了）；如果你指的是時值，請告訴我。

### D1-2 拍線從哪裡來
- 檔案有四分音符、而且音符真的落在拍號格線上（有音的拍裡 ≥ 45% 拍線上有起音）：用拍號格線（複拍子照 cc 換算）。一拍短於 0.36 秒就在小節內兩兩／三三合併（5/8＝2+3、7/8＝2+2+3），長於 1.25 秒就均分（不能一下自動放太久）。
- 否則（SMPTE 沒有四分音符、未量化錄製、速度表跟演奏對不上）：從全曲起音估脈動（起音兩兩的間隔落在週期整數倍附近的程度，偏好 100 BPM 一帶），再沿著起音一拍一拍找（找到起音就落在上面，找不到照週期推，週期只在 0.75～1.33 倍間微調，跟得上 rubato）。
- 弱起不用特別處理：格線從 tick 0 起算，弱起的音落在它真正的那一拍；脈動從第一個起音起算。
- 測資驗證：未量化錄製（真實拍長 0.79 秒±15%）估到中位數 0.76 秒；所有測資的拍線間隔都 ≤ 1.25 秒。
- 替代：Ellis 2007 的動態規劃拍點追蹤。比較準，但程式多一倍；目前的貪婪法在測資上夠用，之後可以換（介面只有 `beatLines(score)`）。

### D1-3 拍子模式的單位頭一定是他自己的音；切分拍「開始這一拍」
- 他這一拍的第一個音就在拍線上：按下去當下響（0ms），跟起音模式一樣。
- 他這一拍的第一個音在拍線之後（切分）：這一下是「開始這一拍」——他帶頭時合奏此刻走到拍線，拍上的音（通常是低音、和聲）當下響，他自己的音照樂譜在拍內出來（預按 `beat`）。這跟休止符鎖同一類：他自己的聲部在拍線上是空的。
- 替代：按下去就放他的切分音（提早半拍）。試過，會把切分拉到正拍、合奏跟著被拖動，測試量到伴奏擠成一團，放棄。

### D1-4 拍子模式的「打拍子」
- 跟著拍子揮的人每一拍都會揮，包括自己的長音還在響的拍。離下一拍的拍線還超過 0.6 拍的那一下記成 `hold`：不加音、不往前，但算他正在彈、而且**進估速**（拍線到拍線）——只用放音的那幾下估速，長音多的聲部速度會越估越慢、合奏越來越拖（測試裡實際發生過）。
- 去抖從「上一下被接受的按鍵」算，另有下限＝這一拍在速度上限（1.6 倍）下的長度的 0.9 倍：亂按最快也只到 1.6 倍。

### D1-5 「一揮跑出好幾個音」
- 起音模式的分組（揮手 0.3 秒內按不及的起音併成一下）是原本的設計，單人手感不能變，所以不改。解法是讓它**看得到**：`scheduler.viewState()` 公布「下一下會放出哪些音」（狀態列與階段 3 的樂譜都畫它）；拍子模式的預告跟實際 100% 一致，起音模式依按下那一刻的速度分組，偶爾差一個（測試要求 ≥ 95%）。
- 想要一下只出一個音的人用音樂家模式（只併真的按不及的），想要一下一拍的人用拍子模式。

### D1-6 快音群
- 三種模式都靠「組內自動放行」：按不及（依目前速度換成真實時間、比這個輸入來源連按的極限還近）的起音照樂譜時刻由電腦放，不管是十六分、三十二分、六十四分顫音、五連音還是 10 tick 的倚音——判斷是真實時間，不看音符種類。
- 拍子模式：拍內所有音都由電腦補上。測試：只跟著拍子揮，12 首 × 2 個聲部 × 鍵盤／揮手 × 三種速度，每個音都響了。

### D1-7 智能切換（`src/midi/modeAdvisor.js`）
- 預設「自動」（從起音開始）。選了固定的模式就不切、只在狀態列給建議。
- 自動只往容易切（亂按、跟不上、只照穩定拍子按 → 拍子；拍子模式卻在照每個音按 → 起音），不會自動升到音樂家（只建議）：音樂家幾乎不擋連按，對不熟的人太容易出錯，這一步留給人決定。
- 切換在按鍵之間生效，切完至少 8 下、6 秒內不再切，不會來回跳。
- 訊號都只跟這首曲子自己的節奏比（按鍵間隔的平均度 vs 放出來的樂譜間隔的平均度、被去抖擋掉的比例、速度被推到檔案的幾倍、落後跳的次數），不看曲名、不靠固定 BPM。
- 主控權：模式怎麼切都不會讓電腦替他放下一拍；只有跟不上好幾拍（第二段防呆）才由電腦小聲代打，他再按一下就接回來。

### D1-8 跟不上：先提示、再小聲介入
- 狀態（`viewState().performers[].state`）：落後一下（錯過一個起音、或落後偏離／脫隊、或停住超過寬限）就是 `behind`，狀態列顯示「落後了，跟著亮點再來一下」；仍跟不上（原本的第二段防呆：錯過 4 下而且離上一下 4 拍以上）才代打，代打的音是原檔力度 × 0.6。
- 替代：一落後就小聲代打。放棄：太快搶走主控權。

### D1-9 拍子模式的速度上限 1.6 倍
- 不懂音樂的人亂揮時歌不會飆走；想彈更快的人用起音或音樂家模式。

### D1-10 已知限制：提早按時 lookahead 已送出的那一顆
- 帶頭的人比合奏預期早按（拍子模式常見：照拍線揮），已經帶時間戳送出（最多 50ms 前）的那一顆伴奏音取消不了（worklet 沒有取消已送出事件的方法），會緊跟在新一拍的音後面響，形成兩個音的倚音般重疊（≤ 50ms）。原本的程式提早按時就有這個現象。測試的「擠成一團」改成量三個以上起音被壓在一起，兩個音的這種情況不算。
- 替代：縮短 lookahead。代價是主執行緒卡住時電腦音會遲到（原本 50ms 就是照實機量到的停頓訂的），不改。

## 階段 2：力度、音量與情緒

### D2-1 力道與表情都是 0～1、0.5 中性（`src/midi/dynamics.js`）
- 中性時（沒有力道資訊、空白鍵、沒有攝影機表情）起音／拍子模式的力度就是原檔的力度，所以現有的使用方式音量不變。
- 起音／拍子模式：原檔力度 × 倍率（力道 0 → ×0.6、1 → ×1.4），保留樂譜本身的強弱起伏。
- 音樂家模式：力度主要由按法決定（24＋103×力道，樂譜只佔 35%）：他掌握「音值」。
- 表情：他自己的音再 ×0.75～1.25；他帶頭時伴奏跟著他的表情 ×0.85～1.15。
- 替代：直接用力道取代原檔力度。放棄：不熟的人一律按同一個鍵，整首會變平。

### D2-2 鍵盤：按鍵左到右的位置
- 依美式鍵盤的實體排列（每排的錯位），最左的字元鍵 0、最右 1，空白鍵 0.5。四排都由左往右遞增。
- 鍵盤手沒有攝影機，他的「表情」用最近幾下的力道平滑出來：一直按右邊的人，伴奏也跟著熱起來。

### D2-3 揮手的力道
- 這一下的深度（尺度單位）與下沉時的最大速度（尺度／秒）：以這個人的尺度（≈肩寬）為單位，站遠站近一樣（測試：尺度 0.09 與 0.28 的同一個揮法，差 < 0.04）。
- 主要跟他自己最近 8 下比（深度、速度各是平常的兩倍各 +0.3），再混 30% 絕對值：動作天生小的人比自己平常大就變大聲；完全不動的人不會被放大。
- 兩手一起揮取大的。

### D2-4 落拍與代打的音量
- 不是帶頭的人落拍（落後偏離／脫隊，或錯過起音）→ ×0.78；電腦代打 → ×0.6；都以 1.2 秒的時間常數漸變（不是一下子掉下去），回來時同樣漸變回 1。
- 帶頭的人不會因為「落拍」變小聲：合奏跟著他，他沒有拍可以落。代打時力道當成中性（不是他按的）。

### D2-5 情緒外接框（`src/vision/expression.js`）
- 框住上半身的節點（鼻子、肩、肘、腕、手掌；看不到的點不算）：坐著時下半身在畫面外也一樣算。
- 大小＝框寬×框高開根號、以尺度為單位（走近走遠不變），手速＝手腕速度（尺度／秒）。一次揮手裡兩者本來就一直變，所以取最近 1 秒的最大值（包絡）。
- energy：跟他自己最近 20 秒比（以中位數為中性、第 10～90 百分位的寬度為尺，寬度有下限擋雜訊）佔 70%，絕對值佔 30%；剛進鏡頭、樣本少時往中性靠；0.6 秒平滑。不在鏡頭時慢慢回到中性。
- 可擴充：`MOTION_PROFILES` 有 `wave`（揮手）、`dance`（緩慢舞動：伸展比速度重要、變化慢）、`conduct`（指揮：速度比大小重要）。目前每個人都用 `wave`；之後新增動作只要加 profile 或換 features → energy 的函式，排程器只吃 energy。
- 畫面：框往外留白、線的粗細與亮度跟著 energy 放大縮小（階段 3 會再整理骨架的裝飾）。
- 測試（合成骨架）：同一個人大而快 vs 小而慢 energy 差 > 0.2；近（尺度 0.3）、遠（0.08）、坐著、邊走近邊揮的 energy 差 < 0.05；動作天生小的人比自己平常大，energy 高 > 0.12。

### D2-6 「聽得出不同的表情」怎麼驗證
- 同一首歌、拍子模式，大而快（力道 0.8、表情 0.8、1.2 倍速）vs 小而慢（0.25、0.25、0.85 倍速）：他的音的力度高 35% 以上、伴奏高 10% 以上、整首短 20% 以上（`test/dynamics.test.mjs`）。真實的聽感要你實機判斷（MANUAL-TESTS M2-3）。
- 只動力度與（已有的）速度，不加檔案裡沒有的音、不改音長。替代：用 CC11／CC74 改音色亮度。沒做：不確定 SpessaSynth 的 GeneralUser 音色對 CC74 的反應，力度最可靠；之後可以加。

### D2-7 還沒按過任何一下的人不給模式建議
- 階段 2 的截圖發現：從頭到尾沒按的 PC 鍵盤手被代打之後被自動切成拍子。他沒有任何按法可以判斷（代打是因為他不在，不是不會），所以 modeAdvisor 在他按第一下之前不建議也不切。

## 階段 3：樂譜視覺化與骨架裝飾

### D3-1 樂譜面板：每人一條、從右往左流
- 舞台底部一排，每位演奏者一條（他的顏色），左邊是狀態文字（performerHud），右邊是他自己的音往「現在」線流過來（橫軸是真實時間：左 0.8 秒、右 5 秒，依合奏目前的速度換算），音高縮放到這個聲部自己的範圍。
- 下一下會放出的音（`viewState().performers[].next` 的 [from, to)）亮起來加白框，頭上一顆大圓點，從圓點拉一條線到「現在」線表示還有多久；拍子模式的圓點在拍線上、拍線畫得比較清楚。放過的音變暗。
- 狀態：落後時圓點閃橘色、整條泛橘；代打中泛紅；休息／等待泛藍；帶頭的人那條框線比較粗。
- 任何 MIDI：每條的音在載入／改指派時排好一次（`scheduler.scoreView()`，快取到計畫重建），每幀只用二分搜尋找畫面內的那一段。端到端測試把 12 首測資（含 SMPTE、未量化、弱起、不規則小節、鼓）逐一載入演奏，每一條都有畫。
- 替代：五線譜。放棄：MIDI 沒有譜號、調號拼法、連結線、聲部的資訊，任意 MIDI 畫成五線譜常常是錯的；長條（piano roll）對任何檔都正確，也比較容易看懂「什麼時候要按」。

### D3-2 骨架裝飾
- 骨頭兩層（寬而淡的光暈＋細實線，不用 shadowBlur）、粗細依這個人在畫面上的大小；頭一圈光暈；兩手腕是「手球」，大小跟著上一下的力道，揮中的那一刻往外擴一圈光環（0.38 秒）；外面一個情緒框（四個角的括號＋很淡的底色）。光暈寬度與亮度、框的大小都跟著表情 energy。
- ID 標籤在頭頂超出畫面時貼著上緣。
- 沒有指定參考，以「在黑幕上看得清楚、跟動作有立即的回饋、不擋到樂譜」為原則自行設計。

### D3-3 主執行緒負擔（無頭 Chromium、4 個假的人揮手、四人合奏 20 秒，同一台機器量原本的程式與現在）
| | 原本 | 現在 |
|---|---|---|
| 每幀視覺處理（追蹤＋手勢＋表情＋畫骨架）平均／p99 | 0.6／2.4 ms | 0.8／2.0 ms |
| 主執行緒佔比（視覺那一段） | 1.1% | 1.7% |
| 樂譜面板每幀 | — | 平均 0.13 ms（30fps） |
| 骨架繪製每幀 | — | 平均 0.33 ms |
- 量法：`__latency()`、`__skeletonStats()`、`__scoreViewStats()`。真實機器（GPU 加速的 canvas）通常更快；請在你的機器上照 MANUAL-TESTS M3-3 量一次。

## 階段 4：上場防呆

### D4-1 操作順序怎麼打亂都能演奏
- 端到端測試用固定種子隨機組合 14 種操作（選歌、指派給鍵盤手／演奏者、取消指派、換模式、換現場人數、開關鏡頭、播放、暫停、重播、試聽、按鍵、鏡頭前的人數變化、重置 ID），每組 16 步。每一步之後檢查：有歌、而且不在處理中時，播放或暫停至少一個能按（沒有卡死的狀態）；最後一定能播、按鍵能放行。預設 6 組，`RANDOM_SEEDS=30` 可以多跑 30 組。
- 程式這部分原本就做得很嚴（播放列的狀態表、單飛的換人數、換歌的請求代號），隨機測試沒有找到卡死的順序，所以沒有改它。

### D4-2 先進場的聲部指派給沒出現的人：不會僵住
- 擔心的情況：合奏在等先進場的人（ghost ID、背對鏡頭的人），後進場的人按了只會被前奏鎖住 → 誰都不能演奏。實測（`test/tracking.test.mjs` 的幽靈 ID）：第一個按下去的人就成為帶頭的人，合奏改跟他走，沒出現的那個聲部錯過之後由電腦小聲代打，所以不會僵住。只留了回歸測試，沒有改排程。
- 所有被指派的人都不在時，合奏停在第一個人的入場點等，舞台中央提示誰該面向鏡頭——這是刻意的：沒有人在演奏時不自動播，主控權在演奏者。

### D4-3 面向鏡頭的提示；看得到臉才鎖定
- 指派了聲部、卻一直沒出現在鏡頭裡（或追丟超過 2 秒）的演奏者：舞台中央寫「演奏者 N 還沒出現在鏡頭裡：請面向鏡頭，讓鏡頭看得到你的臉」；演奏中他那一條的狀態寫「看不到你・請面向鏡頭」（不在鏡頭 1.5 秒以上）。
- 追蹤層鎖定新 ID（開始追蹤、追丟之後重找）要看得到臉（鼻子與至少一隻眼睛可見度 ≥ 0.5）；已經在追蹤的人轉頭、低頭照樣追。MediaPipe 的偵測器本身也是靠臉找人，所以提示請他面向鏡頭。
- 替代：不要求臉，只靠肩膀與可見度。放棄：背景的海報、半個身體容易被鎖成新 ID（幽靈 ID 的主要來源之一）。

### D4-4 幽靈 ID：只有實際出現的 ID 才能演奏，隨時可改
- 指派下拉把鏡頭裡還沒追蹤到的 ID 標成「演奏者 N（未偵測到）」，照樣可以先指派；人出現、揮兩下確認（原本的規則）就能演奏。
- 觸發只來自真的被追蹤到的槽位；不在鏡頭的人照原本的第二段防呆由電腦小聲代打（錯過一下而且不在鏡頭 1 秒）。現場人數、指派、模式都可以在演奏中隨時改（原本就支援從目前位置接續）。

### D4-5 多人靠近時 ID 與骨架不跳到別人身上
- 先用合成的多人場景量（`test/helpers/crowd.js`：靠近再分開、肩並肩、交錯而且後面的人被擋住 1.5 秒、靠過去、四人、四人擠在一起，每幀打亂 MediaPipe 的輸出順序，30% 的幀多吐一組幽靈骨架）：原本的追蹤就不會換 ID。找到並修掉兩個問題：
  1. **追丟回來拿到別人的 ID**：兩個人一起離開、換了順序回來，原本「給第一個空槽位」會讓兩人互換 ID。改成記住被釋放的槽位最後的位置 30 秒，新面孔優先拿離他最近（3 個尺度內）的舊 ID。
  2. **別人的手接到自己身上**：MediaPipe 兩人靠近時會把 B 的手腕接到 A 的骨架上，B 揮手就變成 A 觸發。加了手臂的解剖學上限（上臂 1.6、前臂 1.5、肩到手腕 2.6 個肩寬；真人約 0.9、0.8、1.7）：超過的那一段這一幀不可信，位置停在上一幀、立刻隱藏；兩個人的手部節點幾乎重合時，只有對其中一人是伸到極限（> 1.8 個肩寬）而對另一人比較近，才判定是被借走的手（真的擊掌時兩隻手都保留）。
- 測試也確認正常的揮手（單人、四人、肩並肩、從遠走到近）從來不會被誤判隱藏。
- 真實的 MediaPipe 在兩人重疊時會怎麼錯，合成資料只能模擬一部分：請照 MANUAL-TESTS M4-3 實測，有問題時附上 `copy(__visionLog())`。

### D3-4（上線後修正）黑幕上的版面
- 問題：樂譜面板與狀態格原本照「底下有攝影機影像」設計——半透明黑底在黑幕上等於沒畫；面板（最多佔舞台 42%）疊在骨架之上，揮手最低點與手球的閃光剛好被它蓋住；人頭與 ID 標籤鑽到頂端工具列底下；提示文字的層級在面板之下。
- 決定：
  - 攝影機畫面是黑幕，骨架不必對齊任何影像，所以把整個鏡頭範圍等比例縮放到「頂端工具列與樂譜面板之間」那一段（水平置中，上緣多留 7% 給頭部光暈與情緒框），超出這一段的一律裁掉。面板出現、消失時以 0.25 秒平滑縮放。只改繪製：追蹤、手勢、表情的計算都用原本的座標，不受影響。面板佔多少由 `src/score/layout.js` 傳給 vision.js（顯示、隱藏、改變大小時量一次，不在每幀量）。
  - 面板最多佔 36%（原本 42%），人才不會縮太小；ID 標籤的字級跟著縮小後的大小，人多時不會疊在一起。
  - 條帶與狀態格改用演奏者自己顏色的淡底色，落後／代打的底色更亮；提高已放過的音、框線、拍線、「現在」線、情緒框的亮度。
  - 舞台提示（請面向鏡頭…）的層級提到面板之上。
- 替代：骨架照原位、面板改成全透明。放棄：手在最低點時跟樂譜的音條疊在一起，兩邊都看不清楚。
- 測試：端到端 `skeletonClearOfPanel`（兩個人深揮、四條樂譜時，骨架沒有任何像素畫到面板底下或工具列底下）。

## 整體 UI 優化（減少凌亂）

參考的原則（網路上的設計指引與研究，數字只當起點，要實機驗證）：
- 給長輩的介面：減少畫面上的元素、一次只呈現需要的資訊；文字夠大（桌機約 24pt 以上）、對比至少 4.5:1；重要的狀態不要用藍色（容易看起來褪色）。來源：[uxdesign.cc：A guide to interface design for older adults](https://uxdesign.cc/a-guide-to-interface-design-for-older-adults-31109468d46d)、[UX Planet：Designing for older people](https://uxplanet.org/ux-study-designing-for-older-people-6c67575d9c2f)、[Adchitects：guide to interface design for older adults](https://adchitects.co/blog/guide-to-interface-design-for-older-adults)。
- 音樂遊戲的 HUD：眼睛盯在一小塊區域，資訊要放在周邊視覺看得到的地方、不要讓視線在畫面兩端來回；只留玩家需要的東西，情境資訊需要時才出現；多人時不要把音軌縮到看不清。來源：[Game Developer：Designing HUDs for peripheral vision](https://gamedeveloper.com/design/perceiving-without-looking-designing-huds-for-peripheral-vision)、[Game Developer：Rock Band 3 HUD Analysis](https://www.gamedeveloper.com/design/rock-band-3-hud-analysis)、[Bugnet：How to design a readable HUD](https://bugnet.io/blog/how-to-design-a-readable-hud)。
- 長輩的體感遊戲：互動與回饋要簡單直接。來源：[Gerling 等：Full-body motion-based game interaction for older adults](https://typeset.io/pdf/full-body-motion-based-game-interaction-for-older-adults-3bp52d3f0h.pdf)。

### D5-1 提示放在人身上
- 「ID n」文字改成頭頂一顆他自己顏色的號碼徽章（直徑至少 26px）。徽章外圈是「下一下」的提示：離下一下 1.5 秒內開始慢慢填滿、落後時橘色閃動、電腦代打中紅色、休息／等待灰色。揮手的人盯著自己的骨架就知道什麼時候該揮，不必在人和底下的樂譜之間來回看。
- 樂譜面板保留：它看得到更遠的未來（5 秒），也是 PC 鍵盤手（沒有骨架）唯一的提示。

### D5-2 骨架減法
- 頭改成一個圓；拿掉五官的點、嘴巴三角形與頭部光暈；情緒框只留四個角（拿掉底色）。手球（揮中時的光環）保留：那是「我在控制」最直接的回饋。

### D5-3 面板減法
- 狀態格：名字＋目前的模式（小標籤）一行、狀態一行（字放大），提示只有在有建議或剛切換時才出現，用短句（完整說明放在滑鼠提示）；「自動」「帶頭」不再寫字（帶頭的人框線加粗）。
- 樂譜：拍線只畫給拍子模式的人；之後的音退一階、下一下最亮；休息／等待改中性灰（原本是藍）。

### D5-4 外框
- 演奏中（樂譜面板出現）播放 pill 也淡到 0.55，滑鼠移過去或用鍵盤移到上面才全亮；控制列原本就會淡出。
- 舞台中央的提示（例如「請面向鏡頭」）放大到 1.55 倍、白字深底、黃色框。

### D5-5 沒做的
- 讓使用者自己調整字級：原本的 `--ui-fs` 已經依螢幕寬度與瀏覽器縮放調整，Ctrl +/- 也有效，所以沒有另外做設定。
- 換整套視覺風格（字型、配色系統）：目前的黃色強調色與深色底已經是高對比的組合，這次只做減法與層級，不換品牌樣式。

量測（4 個模擬的人揮手）：視覺每幀平均 1.0ms、骨架繪製 0.37ms、樂譜面板 0.15ms，沒有長任務，跟改版前同一個量級。

## 多人化（PC 鍵盤手＋演奏者 1～4，最多 5 人）

### D6-1 五人的測資與測試矩陣
- 新測資 `quintet`：五個聲部節奏各不相同（八分與十六分快音的旋律、後半拍進的副旋律、全音符長音、兩小節彈兩小節休、走低音）。
- `test/quintet.test.mjs`：5 種模式組合（全起音、全自動、混合、全拍子、全音樂家）× 7 種情境（穩定、速度各不同、兩人中途離開、每個人都亂、一半只跟拍子、有人亂按、鍵盤手沒來），每一組都檢查「絕對不能發生」的事與每個聲部奏完。端到端 `fivePerformers`：四個模擬的人加鍵盤手，五條樂譜、五格狀態、五人都在觸發。
- 基準（單人手感）固定在原本的 12 首，之後新增的測資不放進去。

### D6-2 速度離群的人不能帶頭（找到的問題）
- 現象：五人中有一人亂按（起音／音樂家模式），他的速度估計被推到檔案的 3～5 倍；帶頭的人出狀況時他剛好被選為新的帶頭者，合奏每一下都對齊他，伴奏被擠成一團（最短帶頭時間還保護他 1.2 秒）。
- 決定：至少還有兩個別人正在彈時，速度是那些人中位數的 1.8 倍以上（或以下）的人不能接手帶頭；現任帶頭者一旦這樣，馬上換人（不受最短帶頭時間保護），而且剛被他拖著跳的人也可以接手。一兩個人時不套用（單人手感不變；兩人時判不出是誰離群，硬判會來回換）。
- 測試：亂按的人 8 秒內帶頭不到 1.5 秒，合奏沒有被拖快。

### D6-3 伴奏的表情是大家的
- 原本伴奏的力度只跟帶頭的人的表情。多人時改成一半帶頭的人、一半其他正在彈的人的平均；一個人時跟原本一樣。

### D6-4 五條時的畫面
- 四條以上時狀態格切成緊湊版：名字一行、狀態一行，提示收起來（滑鼠移上去看得到）。

### D6-5 模糊測試（推估「我們沒想到的」情況）
- `test/helpers/fuzz.js`＋`node test/tools/fuzz.mjs <起始種子> <個數>`：隨機產生 MIDI（PPQ 24～960 或 SMPTE、速度 20～300 BPM 並中途亂變、7/16 與 13/8 之類的拍號、1～6 聲部、鼓、和弦、0 長度的音、同音高重疊、很密的音群、30 秒空白、很晚才開始）與演奏（鍵盤手與演奏者 1～4 任取、模式隨機、每個人的行為隨機：照音符、照拍子、太慢、太快、亂按、中途離開又回來、從沒來、漏按多按）。同一個種子產生同一個案例，失敗時可以重現。`npm test` 每次跑 150 個，1000 個案例 0 個問題。
- 檢查：「絕對不能發生」的事（伴奏擠成一團、落後累積、帶頭來回換、多推一步）、有人一直彈到最後時整首要奏完、不能卡住。
- 找到並修好的問題：
  1. 帶頭的人離開鏡頭、沒有別人能接 → 整首停住。改成連續 1 秒不在鏡頭且合奏停在等他：電腦代打他，合奏照樂譜自己走（不是整首自動播：他回來揮一下就接回去）。
  2. 沒有人帶頭、只剩代打的人時伴奏的延音永遠不放。延音的範圍改用「合奏在等誰」（_holdOwner）。
  3. 很稀疏的聲部，揮手確認的期限比他第二個音還早 → 被當成誤觸發移出名單。期限改成至少到他下一個起音之後。
  4. 休止前一刻接手帶頭的人，接手後馬上進休止又交出去 → 他的休止就在眼前時不當候選人。
  5. 音樂家模式被亂按把速度推到 5 倍 → 上限 3 倍（拍子模式原本就有 1.6 倍上限）。
  6. 代打中的人「下一個要按的音」指到代打範圍的尾端（整首的最後），回來的人與畫面上的下一個音標記都以為沒音了 → 代打中改成電腦還沒放的那一個。
- 測試工具本身的修正（不是 app 的問題）：伴奏擠成一團的判斷改成相對於合奏速度、連續 3 個起音才算；帶頭來回換排除彈完、移出、不在鏡頭、休止、速度離群這些本來就該換的原因。
- 刻意不算錯：沒有人一直彈到最後（全員離開、只有亂按的人）時整首停著等，這是規格（不長時間自動播放）。

### D6-6 app 層的防呆（意外錯誤與外部中斷）
- 按鍵、揮手、放開與排程 tick 都包 try/catch：一下出錯只丟掉那一下，錯誤記進 `__faults()`（同一處 5 秒只印一次 console）。排程 tick 連續 3 次出錯（排程器的狀態可能壞了）→ 演奏先暫停、頂端說明，按 ▶ 從原處再試。不自動重新整理：會丟掉選好的歌與指派。
- 聲音被系統暫停（AudioContext 變成 suspended，或 Safari 的 interrupted：換耳機、來電、Siri）→ 演奏先暫停。否則合奏照走卻沒聲音，演奏的人會一直按。按 ▶ 時恢復 AudioContext（使用者手勢）；resume 最多等 1.5 秒（Safari 沒有手勢時可能永遠不 resolve），原本只處理 'suspended'。
- 切到別的分頁、縮小視窗 → 演奏先暫停（瀏覽器會停掉畫面更新與揮手偵測、計時器降到一秒一次，揮手的人會被當成離開）。試聽照樣播。
- 替代方案：自動恢復播放——不採用，回來的那一刻人可能還沒準備好，而且 Safari 要使用者手勢才能恢復聲音。
- 端到端 `interruptions` 模擬這三種情況；真的耳機與來電見 MANUAL-TESTS M4-5。
